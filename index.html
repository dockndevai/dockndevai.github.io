The approach · agents testing their own work

Test Electron & web apps over CDP, not screenshots

For any Chromium-based app there's a better way to let agents test their own changes than computer-use — attach to the app's DevTools instead of driving pixels. mcp-cdp is that tool.

Per-worktree, per-port

Start each agent in its own git worktree, run its own dev build with an explicit --remote-debugging-port, and attach mcp-cdp to that port. Each agent controls only its own app — no two agents fight over one desktop.

The DOM, console & network

Over the Chrome DevTools Protocol the agent reads the real DOM (not a screenshot), and sees what isn't on screen — console errors and failed requests. When a test fails, the reason is right there.

Runs anywhere

CDP works the same on macOS, Linux and Windows — including a headless VPS in the cloud, where OS-specific computer-use can't go. Same flow, any environment.

your-electron-app --remote-debugging-port=9222 && npx -y @dockndevai/mcp-cdp

Safe by default: read-only until you raise the mode, a target allowlist, sign-in pages and browser internals are inspect-only, arbitrary JS is gated behind an explicit flag, and the endpoint is loopback-only. See the mcp-cdp card and the bundled cdp-safe-operations skill.

One governance model

Least privilege, enforced — not documented

Every server shares a pure, unit-tested policy engine. Over-privileged tools are never even advertised to the model; each call is re-checked at runtime.

🔒

Read-only by default

Servers start in read-only mode. Write and admin tools aren't registered until you raise the access mode deliberately.

🎯

Allowlists & protected resources

Scope to specific namespaces, databases, projects or subscriptions. Protected resources can be read but never mutated.

🧨

Delete gating

Destructive operations need the admin mode and an explicit opt-in flag — the most dangerous aren't registered without it.

✍️

Human-in-the-loop approval

Destructive & high-impact actions pause and ask the person to approve — live, via MCP elicitation — before they run. A model can't approve on your behalf.

🧪

Dry-run

Validate and log write intent without executing it — preview exactly what an agent would change.

🧾

JSON audit log

Every guarded operation emits a structured audit line to stderr. Secrets are redacted from all output.

🛡️

Local AI risk guard (optional)

laya-guard classifies high-risk commands (shell, JS eval, apply/delete/exec) allow / confirm / block with a local decision model before they run. Defence in depth that only ever tightens, never grants; fails closed; fully on-device. Wired into every mutating server in the suite (15 servers) — off by default, enabled per-server with one flag.

🧩

One shared core

Every server is built on mcp-core — a single audited governance library (access modes, guard, allowlists, elicitation, symlink-safe paths, audit) on npm as @dockndevai/mcp-core. One implementation, not eighteen that drift.

Get started

Add one to your agent in a minute

Every server is a standard stdio MCP server on npm. Here it is in Claude Code — start in read-only and raise the mode when you need to.

# Claude Code — mcp-kubernetes, read-only
claude mcp add kubernetes \
  -e K8S_MODE="read-only" \
  -- npx -y @dockndevai/mcp-kubernetes

# Or wire any server into claude_desktop_config.json:
{
  "mcpServers": {
    "kubernetes": {
      "command": "npx",
      "args": ["-y", "@dockndevai/mcp-kubernetes"],
      "env": { "K8S_MODE": "read-only" }
    }
  }
}
  1. Pick a server from the Products menu and copy its npx command.
  2. Start read-only. Every server boots in the safest mode; only read tools are exposed.
  3. Raise the mode deliberately when you need writes — read-write, then admin plus an opt-in flag for anything destructive.
  4. Per-client setup (Claude, Cursor, Codex, VS Code, Windsurf) is in each repo's docs/CLIENTS.md.
